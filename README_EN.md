FluentHMI Studio is a C++/Qt 6 rewrite of [PyQt UI Designer](https://github.com/txp666/PyQt-UI-Designer): drag widgets onto a canvas, set their properties, bind them to serial, TCP or MQTT data, then export the design as a standalone app, with **no compiler needed**. Compared with the Python version, the download is smaller, it starts about twice as fast, exports take under a second, and it can update itself from inside the app (see [Compared with the Python version](#compared-with-the-python-version)).

> **Language**: the interface is in Chinese for now; an English interface is on the [roadmap](#current-status-010).

## Let AI write the project

A `.uidp` file is JSON. Give Claude, Codex or another AI your requirements together with this link, and it can write the project file directly:

```text
https://raw.githubusercontent.com/txp666/FluentHMI-Studio/main/docs/uidp-format.md
```

This is the raw text of [docs/uidp-format.md](docs/uidp-format.md), which an AI can read in one go without opening a web page or cloning the repository. The guide is written in Chinese, and AI assistants can read it as it is. It has the rules, a complete example and a list of widgets; every property of every widget is in [docs/uidp-widgets.md](docs/uidp-widgets.md), which is generated by the program and linked from the guide for when it's needed. When the file is written, check it with `FluentHMIRuntime project.uidp --check`, then open, preview and export it in Studio.

## Compared with the Python version

Both use the same project format, and their widget and protocol rules match:

- **Compatible project format**: it reads and writes `.uidp` (version 1.0) directly, and its widget types, property names, default values and enum options match PyQt UI Designer one to one. All 9 example projects in `examples/` open, preview, and save back unchanged.
- **Same parsing and binding rules**: the four parsers (line text with key-value / JSON / CSV, HEX frame, Modbus RTU, Modbus TCP), the four kinds of binding (key-value matching / JSON path / HEX byte extraction / Modbus) and the three command encodings (text / HEX / Modbus) were ported from the Python version rule by rule and are covered by unit tests.

The differences are in how they are built and how they export apps:

| | FluentHMI Studio 0.1.0 | PyQt UI Designer 0.1.6 |
| --- | --- | --- |
| Implementation | C++17 / Qt 6, compiled natively | Python / PyQt5 (Qt 5), packaged with Nuitka |
| Exporting an app | Copies a prebuilt runner and adds the project and images, about 0.3 s, no Python or compiler needed | Generates Python source, then compiles it with Nuitka; the downloaded designer needs Python and build tools installed separately to package |
| Preview and export | The preview and the exported app are the same runner, so the preview shows exactly what the export will look like | The preview runs inside the designer; the export is separately generated code |
| macOS package | One universal package, 32.7 MB (76 MB unpacked), for both Apple Silicon and Intel; exported apps are universal too | One package each for arm64 and x64, 53.8 / 62.8 MB (155 MB unpacked for arm64); packaging only builds for the local architecture |
| Windows package | 16.7 MB | 54.2 MB |
| Time to first window | 0.7–1.1 s | 1.5–2.2 s |
| Memory after startup | 71–85 MB | 126–137 MB |
| Updates | Checks, downloads, verifies and replaces itself in the app; can check at startup | Manual check on the settings page, which opens the download page when there is a new version |

Package sizes are taken from each project's GitHub Release. Startup and memory were measured on the same Mac (Apple M5 Pro, 48 GB, macOS 27.0.1) with the Apple Silicon builds of both versions: an empty project, launched 4 times each, counting the last 3 (the first launch took 2.0 s and 3.9 s respectively); memory is the resident memory 5 seconds after the window appears. The export time is from exporting `examples/demo.uidp` three times (0.26–0.41 s).

What the Python version still has and this one doesn't yet: exporting a source project you can keep editing, and the live chart's cursor and data save / load (see the roadmap below).

## Architecture

```
src/core      fhmi_core     Project model, widget metadata, protocol parsing, data binding, command encoding (Qt Core only)
src/comm      fhmi_comm     Link interface + serial / TCP client / TCP server / MQTT; CommHub gathers all links
src/runtime   fhmi_runtime  Runtime widgets built on FluentQtWidgets, RuntimeSurface, binding engine
src/designer  fhmi_designer Canvas (QGraphicsScene), widget panel, property editor, alignment and container nesting
src/studio    FluentHMIStudio   The designer app: design / preview / settings pages, export service
src/player    FluentHMIRuntime  The runner for exported apps: reads the project.uidp next to it (or inside the .app)
tools         uidp_reference    Regenerates docs/uidp-widgets.md and the widget list at the end of docs/uidp-format.md from the widget registry
```

The design canvas shows the real runtime widgets, wrapped in QGraphicsProxyWidget and ignoring the mouse. The preview and exported apps attach the same widgets to a RuntimeContext, which receives data from the links, applies the bindings and sends commands.

## Building

Requires CMake 3.21+, C++17 and Qt 6.5+ (Core, Gui, Widgets, Svg, Network, SerialPort).

```bash
git clone --recursive https://github.com/txp666/FluentHMI-Studio.git
cd FluentHMI-Studio
cmake --preset debug
cmake --build --preset debug
ctest --preset debug
```

On macOS, run `open build/debug/FluentHMIStudio.app`. To export without the UI:

```bash
FluentHMIStudio --export <output-dir> <project.uidp>
```

The runner can render a whole project to an image; the widget overviews in `docs/images` were made this way:

```bash
FluentHMIRuntime <project.uidp> --theme dark --screenshot widgets-dark.png
```

## Online updates

Studio gets updates from this repository's GitHub Releases. The settings page has a Check for updates (检查更新) button and a Check for updates at startup (启动时检查更新) switch, which is on by default; the startup check only shows a dialog when it finds a new version, and stays quiet on network errors. When a new version is found, it shows the release notes, and you can update now, skip this version or decide later.

Updating now downloads the package for your platform (`-macos-universal.zip` / `-windows-x64.zip`), checks its size and SHA-256 against the `.sha256` file in the Release, and unpacks it into a `.fluenthmi-update` folder next to the install folder. Then click Restart and update (重启并更新), or quit Studio later, and a small helper script (sh on macOS, PowerShell on Windows) waits for Studio to exit, moves the old version aside, puts the new one in its place, restarts it if asked to, and finally deletes the old version. If the new version can't be put in place, the script restores the old one, and the next launch tells you why. When Studio runs from a build folder, from a quarantined temporary location on macOS, or without permission to write to its install folder (for example under Program Files), it doesn't update itself and opens the download page instead.

To update without the UI (the package is replaced after this process exits):

```bash
FluentHMIStudio --update
```

To test the update flow, point `FHMI_UPDATE_URL` at a JSON file on a local server in the same format as GitHub's "latest release" API. While a repository is private, GitHub answers anonymous requests with 404, and the update check reports that no published release was found.

## Packaging and releases

```bash
cmake --preset release && cmake --build --preset release
python3 scripts/package.py --build-dir build/release --output-dir dist
```

On macOS this produces `FluentHMI Studio.app`, with the runner at `Contents/Helpers/FluentHMIRuntime.app`; on Windows it produces `FluentHMI-Studio/`, with the Studio and runner exes in the same folder. The package holds a single copy of Qt: on macOS Qt lives in the runner and Studio uses it through its rpath and `qt.conf`; on Windows both share the Qt DLLs and plugins in the folder, and `runtime-files.txt` lists the files the runner needs. Exporting an app copies only the runner and its Qt, which is why exported apps can be copied straight to another computer and run. At the end, the script exports `examples/demo.uidp` with the packaged Studio and starts the exported app with `--check`; if any step fails, no archive is produced. On macOS it also checks that no library is still loaded from the build machine's Qt folder, and uses `DYLD_PRINT_LIBRARIES` to confirm that at run time Studio and the exported app load only system libraries and libraries inside the package. The output is a zip plus a `.sha256` file; macOS builds are only ad hoc signed, without Developer ID signing or notarization.

To release a new version, change `project(... VERSION ...)` in `CMakeLists.txt`, optionally add `docs/release-notes/vX.Y.Z.md`, then push a `vX.Y.Z` tag. The `Release` workflow builds, tests and packages on Windows and macOS (universal), and only publishes the GitHub Release when everything passes.

## Current status (0.1.0)

Done: all 29 widgets, drag-and-drop design, grid snapping, zoom, alignment and distribution, container nesting (horizontal / vertical / flex / card / tab), property and data binding editing, save / open / save as (relative image paths follow the project folder when it moves), serial / TCP / MQTT preview, standalone app export, Windows and macOS packaging, light and dark themes, Fluent-style scroll bars everywhere, and online updates (check, download and verify, replace and restart).

The MQTT link is a built-in MQTT 3.1.1 client (based on QSslSocket, so the Qt MQTT module isn't needed): it supports username and password, QoS 0/1/2, `+`/`#` wildcard subscriptions, and TLS with the system certificate store, and it reconnects automatically if a connection that succeeded drops. As in the Python version, each message is treated as one frame, and a payload that is a single plain number is also given with the topic name as its key.

Tested end to end on macOS: data display, charts and commands with simulated TCP and MQTT devices, running exported apps, and unpacking and running a package built on the same machine. The Windows package runs an export self-check in the release workflow (Windows Server 2022), and unpacking and running it, exporting, and running the exported app have been checked in a Windows 11 ARM64 virtual machine (under x64 emulation). Not verified yet: connecting to a real MQTT broker, and TLS.
